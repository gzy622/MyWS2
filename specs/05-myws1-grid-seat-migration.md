## 1. 目标

在保留本项目三页双子视图导航、移动端手势、现有视觉基线和零依赖原生技术栈的前提下，分阶段迁移 MyWS1 网格与座位表的完整业务能力：

- 学生完成登记、计分和清除记录。
- 作业切换及增删改。
- 网格与座位表共享同一份业务状态。
- 座位查看、编辑、移动、交换、复位、平移和缩放。
- 批量标记、清除、复制未交名单和恢复默认数据。
- 严格业务持久化、深色模式、横屏布局和软键盘适配。
- 与上述行为对应的可访问性、错误处理和验证覆盖。

本方案只定义执行顺序和完成门槛，不在单个阶段顺手迁移安排页、课程页或 MyWS1 的其他业务模块。

## 2. 执行原则

1. **按依赖推进**：先建立领域状态和数据校验，再接入网格，之后让座位表复用；不得分别为两个视图维护登记状态。
2. **每阶段可独立验收**：阶段结束时应用必须可启动、旧功能可回归，不留下只在后续阶段才可运行的半成品。
3. **状态只有一个业务来源**：UI 瞬时状态与业务数据分层，但同一份学生、座位、作业、提交或分数不得存在两个可写副本。
4. **迁移行为，不照搬框架**：MyWS1 使用 Vue/TypeScript；本项目继续使用原生 HTML、CSS 和 ES Modules，不引入 Vue、构建工具或第三方依赖。
5. **保留现有契约**：继续保留 `data-page`、`data-index`、`data-sub`、`data-view`、`data-action`、三页导航和底部导航手势。
6. **先更新约束再实现冲突项**：持久化、深色模式和短横屏 10 列与当前 Spec 冲突，必须在对应代码提交前完成 Spec 决策。
7. **分批提交**：领域、网格、浮层、座位、菜单、持久化和响应式能力分别提交，避免一个提交同时改写所有模块。

## 5. 目标架构

### 5.1 状态边界

```text
scripts/state.js
└─ UI 瞬时状态
   ├─ currentPage / subviews
   ├─ drawerOpen / activeOverlay
   ├─ studentFontSize / fontSizePopoverOpen
   ├─ seatEditing
   └─ suppressNavClick

scripts/roster-store.js
└─ 唯一业务状态
   ├─ students
   ├─ seats
   ├─ assignments / activeAssignmentId
   ├─ submissions
   ├─ scores
   └─ nextAssignmentId

scripts/roster-storage.js
└─ 只负责严格读取、迁移和写入业务状态
```

规则：

- 组件或交互模块只调用 Store 方法，不直接修改业务数组。
- Store 方法负责校验、关联清理、交换座位和触发保存。
- 渲染器订阅 Store 变更并更新两个视图。
- `scripts/state.js` 不复制学生、座位、作业、提交和分数。
- 浮层草稿只保存在浮层模块内，确认后才写入 Store。

### 5.2 业务数据结构

```js
{
  schemaVersion: 1,
  students: [{ id: 1, name: '赵予安' }],
  seats: [{ studentId: 1, seatIndex: 17 }],
  assignments: [{ id: 1, name: '作业 1' }],
  activeAssignmentId: 1,
  submissions: [{ assignmentId: 1, studentId: 1 }],
  scores: [{ assignmentId: 1, studentId: 1, value: 95.5 }],
  nextAssignmentId: 1
}
```

必须保证：

- 学生 ID、作业 ID、座位索引唯一且引用有效。
- 每名学生恰有一个座位，座位索引位于 `0～103`。
- 同一作业和学生最多一条提交、最多一个分数。
- 有分数即视为已完成；清除完成记录时同步清除分数。
- 至少保留一个作业，活动作业必须存在。
- 分数为 `0～100`，最多一位小数。
- 无法严格解析的持久化数据整体回退到默认值，不把半合法数据送入 Store。

### 5.3 建议文件职责

| 文件 | 职责 |
| --- | --- |
| `scripts/roster-model.js` | 常量、默认学生、默认座位、默认作业和纯校验函数 |
| `scripts/roster-store.js` | 业务状态、查询方法、变更方法和订阅通知 |
| `scripts/roster-storage.js` | Schema 解析、版本迁移、异常捕获和持久化 |
| `scripts/roster-renderer.js` | 网格与座位卡的共享状态渲染 |
| `scripts/student-interactions.js` | 学生轻点、长按、右键和点击抑制 |
| `scripts/student-record.js` | 学生记录面板、分数草稿、校验和焦点 |
| `scripts/assignments.js` | 作业列表及新增、改名、删除流程 |
| `scripts/seat-geometry.js` | 13×8 座位几何的唯一常量来源 |
| `scripts/seat-canvas.js` | 平移、缩放、惯性、卡片手势、编辑拖放和复位 |

若执行中证明某个模块职责过小，可合并相邻模块；不得把全部业务重新塞入 `main.js`、`navigation.js` 或 `index.html`。

## 8. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 网格和座位分别维护状态导致不同步 | 所有变更只进入 `roster-store.js`，两个视图只订阅渲染 |
| 长按、座位拖动和页面横滑冲突 | 明确手势所有权；座位视口阻断页面手势；所有路径有 cancel 和 click 抑制 |
| 重新渲染座位 DOM导致 transform 丢失 | 画布 transform 独立保存在 `seat-canvas.js` 内存；状态更新只更新卡片，不重建 stage |
| 持久化坏数据导致启动失败 | 严格解析、版本迁移、整体回退、存储异常捕获和单元测试 |
| 主题引入两套漂移样式 | 只扩展 token，组件继续引用语义变量 |
| 输入法导致背景压缩和焦点循环 | 使用 Visual Viewport；打开输入前锁定背景高度；resize 不主动 blur |
| 单次改动过大难以回归 | 严格按阶段提交，每阶段通过门槛后再进入下一阶段 |
| 当前 Spec 与迁移目标冲突 | 阶段 0 先修改并评审 Spec，后续实现引用已更新契约 |

## 9. 提交与回退策略

- 每个阶段至少一个独立 Conventional Commit，不将多个阶段压成一次提交。
- 领域和存储提交必须先于依赖它们的 UI 提交。
- 阶段失败时优先回退当前阶段提交，不回退已经验收的基础阶段。
- 不用 feature flag 长期保留两套网格或座位实现；确需过渡时只允许在同一阶段内存在，并在阶段提交前删除旧路径。
- 每次提交前执行该阶段最小验证和 `specs/03-engineering.md` 的通用检查。
